# Talos Learning Roadmap

This file is the shareable curriculum and working plan for the Talos learning journey.

## Mission

Become a Talos Champion: someone who can confidently design, bootstrap, secure, operate, upgrade, and troubleshoot production-grade Talos Kubernetes clusters across bare metal, Proxmox, and cloud environments.

## Teaching approach

Each concept should be taught in this sequence:

1. Explain the problem it solves.
2. Explain how Talos implements it.
3. Compare it with traditional Linux/Kubernetes patterns where useful.
4. Show the relevant commands.
5. Explain every important command flag.
6. Explain what happens internally after the command runs.
7. Identify the credentials, certificates, keys, tokens, or configuration files involved.
8. Show how to verify that it worked.
9. Include common failure scenarios and systematic troubleshooting.
10. End with a small hands-on lab or challenge.

Do not provide commands without explaining their purpose, execution location, required permissions, expected output, and security implications.

## Phase overview

1. Talos mental model
2. CLI and API understanding
3. Security artifacts and trust relationships
4. Cluster lifecycle
5. Installation patterns
6. Boot and Secure Boot
7. Production security
8. Troubleshooting like an SRE
9. Operations at scale

## Detailed phase expectations

Each phase should contain:
- mental model
- architecture or trust diagram
- command reference with explanations
- security considerations
- production best practices
- common mistakes
- troubleshooting playbook
- hands-on lab
- verification checklist
- five interview questions
- a Talos Champion challenge

## Phase 1 — Talos mental model

Teach:
- what Talos Linux is and what problems it solves
- immutable and API-driven OS management
- why Talos has no SSH, package manager, or interactive shell
- Talos architecture and system services
- Talos API and Kubernetes API boundaries
- control plane, worker, bootstrap, endpoint, and node concepts
- machine configuration and patches
- installation versus cluster bootstrap
- what persists across reboots and upgrades
- how Talos differs from Ubuntu/RHEL-based K8s nodes
- when Talos is and is not the right choice

## Phase 2 — Understand every CLI

### talosctl

Explain:
- what it controls
- which API it communicates with
- endpoint versus node selection
- how talosconfig is created and used
- authentication and authorization
- certificate-based access
- important command groups: configuration, installation, health, logs, networking, storage, upgrades, Kubernetes access, recovery

Example syntax:

```bash
talosctl --endpoints <endpoint> --nodes <node> <command>
```

Clarify the difference between `--endpoints` and `--nodes` using realistic multi-node examples.

### kubectl

Explain:
- what it controls in a Talos-based cluster
- why kubectl cannot manage the Talos OS
- how kubeconfig is generated and used
- Kubernetes authentication and RBAC
- how kubectl and talosctl complement each other
- how to decide which CLI to use during an incident

### omnictl

Explain:
- what Omni adds on top of Talos
- which Omni API it communicates with
- how Omni manages machines, clusters, templates, upgrades, and access
- Omni authentication and authorization
- how Omni-generated access differs from standalone Talos access
- what requires Omni and what can be done with open-source Talos alone
- licensing or edition dependencies that may affect a design

Also cover related tools as needed: helm, cilium, crictl, image factory, installer tooling.

## Phase 3 — Security artifacts and trust relationships

Explain every important artifact created during a Talos installation, including:
- talosconfig
- kubeconfig
- machine configuration files
- secrets bundle
- cluster CA
- machine CA
- Kubernetes CA
- etcd CA and certificates
- service-account keys
- bootstrap tokens
- discovery or join information
- administrator certificates
- Omni credentials and machine identities
- Secure Boot keys and signatures, where applicable

For each artifact, document: generated by, generated when, used by, access granted, storage, rotation and revocation, exposure impact.

Also cover:
- what must not be committed to Git
- what can be stored in Git
- how to use SOPS, age, Vault, or similar systems
- certificate expiration and rotation
- least privilege and break-glass access
- removing access for departed administrators
- recovering lost talosconfig or kubeconfig
- why kubeconfig and talosconfig are different risks

## Phase 4 — Cluster lifecycle

Teach the full lifecycle:
1. Select or build the Talos image
2. Boot with ISO, PXE/iPXE, virtual media, or disk image
3. Discover machines
4. Generate secrets and machine configurations
5. Apply control-plane and worker configs
6. Bootstrap etcd exactly once
7. Retrieve kubeconfig
8. Install or configure the CNI
9. Join additional nodes
10. Validate cluster health
11. Upgrade Talos
12. Upgrade Kubernetes
13. Replace a failed node
14. Scale control-plane and worker nodes
15. Back up and restore etcd
16. Reset, wipe, or decommission nodes safely

Discuss internal behavior and destructive/reversible steps.

## Phase 5 — Installation patterns

Cover production-oriented patterns for:
- local VM lab
- Proxmox
- bare metal
- PXE/iPXE at scale
- DHCP and network boot
- air-gapped environments
- AWS or another cloud example
- standalone Talos without Omni
- Talos managed through Omni
- GitOps-driven provisioning
- creating tens or hundreds of consistent clusters

Include factory/image-factory ideas, schematic IDs, system extensions, kernel arguments, platform-specific images, disk selection, predictable network config, VIP and LB options, endpoint design, and DNS/NTP/DHCP dependencies.

## Phase 6 — Boot and Secure Boot

Teach the complete boot chain:
- BIOS versus UEFI
- ISO, disk, PXE, and iPXE boot
- installer image versus installed OS
- maintenance mode
- Secure Boot and measured boot
- UKI and image signing where relevant
- custom Secure Boot keys
- machine identity and node attestation
- what Secure Boot protects and what it does not

## Phase 7 — Production security

Cover:
- Talos API exposure
- Kubernetes API exposure
- firewall and network-policy requirements
- certificate-based authentication
- bastion, VPN, and private-network flows
- disk encryption and TPM integration
- etcd encryption and backup protection
- Kubernetes secret encryption
- workload identity, admission policies, image signing, audit logging
- supply-chain security and hardened operations

Separate Talos, Kubernetes, Omni, and external infrastructure controls.

## Phase 8 — Troubleshooting like an SRE

Use a repeatable framework:
1. Identify the failure layer.
2. Collect evidence before changing anything.
3. Use the least disruptive diagnostic command first.
4. Explain the healthy state.
5. Compare it with the observed state.
6. Apply the safest corrective action.
7. Verify recovery.

Cover tools and techniques for cluster health, service state, logs, kernel logs, processes, networking, DNS, NTP, disks, etcd, Kubernetes static pods, kubelet, CNI, certificates, configuration drift, failed upgrades, boot loops, and node replacement.

## Phase 9 — Operations at scale

Teach production operating practices for:
- declarative machine configs
- patch strategy
- secrets separation
- repo structure and environment promotion
- cluster templates
- automated validation
- controlled upgrades and rollback
- drift prevention
- fleet inventory
- observability
- backup and disaster recovery
- compliance evidence
- managing hundreds of clusters

Use one realistic example: building a repeatable platform for 100 Talos clusters across multiple sites.

## Accuracy and currency

Use current official Talos Linux, Omni, and Kubernetes documentation as primary sources. State the versions assumed in each lesson.

Label clearly:
- stable features
- experimental features
- deprecated commands or behavior
- version-dependent behavior
- Omni-only or commercially licensed capabilities

Do not invent commands, flags, files, or security behavior. If something is uncertain or version-specific, verify it and say so.

## Monthly update routine

At the end of the learning program, maintain a routine covering:
- Talos release notes
- Kubernetes compatibility
- Omni changes
- security advisories
- deprecated APIs and commands
- new system extensions
- upgrade recommendations
- important documentation changes

Maintain a “What changed since my last lesson?” section so knowledge can be refreshed without repeating the entire course.

## Recommended learning sequence

Start with:
1. complete phased roadmap
2. CLI and API mental model
3. security-artifact lifecycle overview
4. recommended lab environment
5. Phase 1, Lesson 1

Keep the lessons practical, precise, and oriented toward real production ownership. Challenge incorrect assumptions and explain the reasoning behind corrections.
